Build Fieldnote Board, a complete local-first task application for a small project team. It is a fictional, local-only demonstration. Deliver vanilla index.html, styles.css and app.js (additional local modules allowed), with no build step, dependency installation, external resources, network API, authentication or backend. It must run from any static server and a nested URL path using relative assets. Work independently and finish implementation and your own verification within the run deadline. Produce a considered, coherent dashboard design at mobile 360px and desktop 1440px, useful empty/error states and accessible keyboard interactions; design quality matters too.

Functional contract:
1. Persist a board in localStorage key "fieldnote-board:v1" using {schemaVersion:1,tasks:[...]}. Each task has exactly these meaningful fields: id (unique nonempty string <=80 characters), title (trimmed nonempty string <=120), project (trimmed nonempty string <=80), status ("todo", "doing", "done"), priority ("low", "medium", "high"), dueDate ("" or a real calendar date in YYYY-MM-DD), tags (array of at most 8 trimmed nonempty strings <=24). For user comma-separated tags, trim and deduplicate case-insensitively. Seed a useful fictional board on genuinely empty storage only; use at least 6 tasks, 2 projects and all 3 statuses. Do not overwrite existing corrupt data on startup.
2. Create and edit tasks; changing one preserves other records. A form data-testid="task-form" has named inputs/selects title, project, status, priority, dueDate, tags; tags accepts comma-separated text. A visible "New task" button has data-testid="create-task" and a submit button data-testid="save-task". Reject blank titles, overlong text and invalid dates with visible errors. Use generated unique IDs.
3. Render each task as data-testid="task-card" with data-task-id equal to its ID. It contains controls data-action="edit" and data-action="delete". Editing opens the form with existing values. Provide a status control data-action="status" on each card (native select). Deletion is reversible via a visible data-testid="undo-delete" button; undo restores the exact record and persists across reload once restored.
4. Combine search (data-testid="search", case-insensitive across title/project/tags) with filters data-testid="filter-status", "filter-project", "filter-priority". Each filter uses a native select with "all" sentinel plus the corresponding actual values. Reflect only matching cards; offer a useful no-results state. Keep a visible total/matching count. Treat imported text as text, never HTML.
5. Export the full board, including filtered-out records, as JSON using data-testid="export". Import via input type=file data-testid="import-file"; selecting a file offers explicit confirmation before replacing the board. Accept only valid schemaVersion 1 documents up to 1 MiB. Reject duplicate IDs, unsupported enums, invalid dates, oversized input and malformed JSON. Import is atomic: any invalid task must leave the entire prior board untouched. Show a useful error; a valid confirmed import replaces the board and survives reload. Native confirmation dialogs are acceptable.
6. If storage is corrupt on startup, preserve its exact bytes and show a visible recovery notice; do not silently seed or overwrite. Provide an explicit reset after user confirmation and a way to download the original bytes. If storage writes throw, show that the change is not saved; do not claim persistence. Keep work recoverable in memory or the form.
7. If another tab writes the storage key, show a visible conflict/reload notice and block stale destructive edits until the user explicitly reloads the board, or implement and explain an equally safe reconciliation. Never silently overwrite newer external state.
8. All UI controls need meaningful accessible names and keyboard support. On a modal form, close on Escape and restore focus. Reduced-motion preference must suppress nonessential animations. The app must show a useful message when JavaScript is disabled.
