## Design for a calendar‑and‑inbox scheduling assistant

**The core mechanism: a four‑way triage run on every incoming item, not a single "is this urgent" check.**

Every calendar event and every inbox message that touches scheduling gets scored on three independent axes before a mode is picked: how reversible the resulting action is, how much it commits the user to something outside their already‑stated preferences, and how much judgment or relationship context the reply requires. Those three axes, not the sender or the subject line, decide whether the assistant acts, asks, hands off, or ignores.

**Ignore** is the default for anything that requires no decision: an invite the user already accepted or declined, a meeting reminder, a newsletter, a "no reply needed" confirmation, a thread where the user is cc'd but not addressed, or a message that arrived after the relevant event already resolved itself. Ignoring is logged, not silent — everything ignored still shows up in the digest described below, so nothing is invisibly dropped, but no action or reply is generated.

**Act** is reserved for items that are both fully reversible and already covered by a standing rule the user has set — a declared availability window, a rule for how conflicts resolve, a policy on which recurring meetings to auto‑accept, a list of people whose invites are always confirmed. Within that envelope the assistant may accept an invite that fits the stated hours and has no conflict, decline a duplicate or clearly conflicting invite when a rule already says which one wins, send a plain logistical acknowledgment ("received, confirming Tuesday 3pm, dial‑in attached"), rebook around a cancellation into an equivalent slot, or forward a meeting's existing details to a participant who asked for them again. It never acts on anything that wasn't pre‑authorized by an explicit rule — a plausible-looking judgment call is not the same as a covered case, and the assistant treats the absence of a rule as a "no," not an invitation to improvise.

**Ask** covers everything that's reversible in principle but not covered by a standing rule, or where the tradeoff itself is the decision — two invites that both matter and only the user knows which to prioritize, a request to move a meeting that others have already confirmed, an invite from someone flagged as important where tone matters, anything that would set a new precedent ("should I start auto‑accepting these going forward?"), or a correspondent negotiating terms of a meeting rather than just picking a time. Every "ask" carries a proposed action, a deadline for the user to weigh in, and a stated default the assistant will fall back to if that deadline passes unanswered — always the most conservative, easiest‑to‑undo option (a tentative hold rather than a firm accept, a polite "let me check and confirm shortly" rather than a decline). That default is what keeps the system from stalling correspondents during a long silence, and it's disclosed to the user up front, not sprung on them after the fact.

**Handoff** is for anything past scheduling mechanics: substantive questions embedded in a scheduling thread (contract terms, pricing, a personal or medical matter, anything with legal or financial weight), a correspondent explicitly asking to reach the user directly, a complaint or conflict that needs the user's own voice, or a request that depends on relationship history or judgment the assistant has no access to. A handoff item gets a holding reply if a reply is unavoidable in the moment ("I'll make sure this reaches [user] directly"), and is flagged to the user as something only they can answer — the assistant does not attempt a substantive reply on their behalf, ever.

**What it may send while the user is unreachable for hours.** The unreachable window doesn't create new authority — the same act/ask/handoff boundaries hold, but everything sent in that window is restricted to messages that carry no firm commitment and are trivially reversible: acknowledgments of receipt, requests for available times, tentative holds (explicitly marked tentative, never presented as confirmed), routine logistics (time zone conversion, dial‑in or address details, rescheduling links), and polite deferrals that buy time without promising an outcome. It will not send firm confirmations or declines of anything not already covered by a standing rule, financial or contractual language, anything that alters a plan other people are already relying on, or any message that speaks for the user's judgment rather than their calendar. If a genuinely time‑boxed item arrives that exceeds this envelope — something needs a real answer before the user is expected to resurface — the assistant sends only the most conservative holding message it's permitted to send and escalates through the reach‑the‑user channel below; it does not guess at what the user would want just because the clock is running.

**How it identifies itself.** Every message it sends discloses, plainly and in the same message, that it is a scheduling assistant acting on the user's behalf and not the user personally — a short signature line to that effect, with a way for the recipient to ask to be routed to the user directly. This applies uniformly, including to messages whose wording the user pre‑approved; the disclosure is about who is transacting, not about how polished the prose sounds. The point is that no recipient is ever left believing they negotiated directly with the user when they didn't — that's a trust and consent issue independent of how good the assistant's writing is.

**How it reaches the user.** The assistant never routes anything to the user through the same inbox it's managing — that channel is already the problem it exists to filter. Instead it uses one dedicated, low‑noise channel with three tiers. Routine, non‑time‑boxed items — everything it acted on, everything it asked and got answered, everything it's still waiting on — go into a standing digest the user reviews whenever they resurface; nothing in this tier interrupts. Items that need a real answer but aren't on a hard clock get queued as pending questions in that same digest, each carrying its stated deadline and default action, so the user can process a backlog in one pass without anything having silently expired wrong. Only items with a genuine deadline that will pass before the user is expected to resurface use an interrupt‑level notification, and even that notification states the deadline, the options, and exactly what the assistant will do by default if no reply arrives in time — so being unreachable through an interrupt never leaves the user surprised by what happened while they were away. Handoff items are marked distinctly from ask items in all three tiers, since they need the user's own words, not just their yes or no.
