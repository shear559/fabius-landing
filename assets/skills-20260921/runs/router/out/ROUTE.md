# Routing plan — Inkwell public API launch

Four independent deliverables, routed separately. "Machinery" follows the fabius capability ladder (R2–R3): stay at the smallest rung that holds a high-quality answer — a single-pass draft, one specialist skill, no swarm, unless the task itself has parallel/independent sub-parts.

| # | Part | Fabius skill(s) loaded | Machinery | Model tier | Why |
|---|------|------------------------|-----------|------------|-----|
| 1 | Rate-limiting design for the API | `fabius-disciplina` (system design: evidence, alternatives, proof) under `fabius-parcus` | Single-pass design doc: one agent, no swarm — algorithm choice (token bucket vs sliding window), key (per-API-key vs per-workspace), storage (existing Redis), behavior across the 4 LB'd instances, 429/header contract, tier mapping to the numbers already given (60/600/3000 rpm) | **Strong** | Real architectural judgment under ambiguity that's expensive to get wrong later: race conditions across 4 stateless instances sharing Redis, burst vs sustained limits, what happens at tier boundaries. Not mechanical — this is exactly the "architecture, ambiguity" case routing-policy R11 reserves the strong tier for. |
| 2 | Threat model of sign-up + API-key flow | `fabius-praesidium` (STRIDE per trust boundary, OWASP pass) | Single-pass STRIDE grid over 2–3 trust boundaries (client→signup, signup→key-issuance, key→API), no swarm, no offensive tooling (defensive only) | **Strong** | Security judgment on a flow that gates a *paid* public API — wrong calls here (e.g. unthrottled signup, key shown once vs logged, Google-vs-password parity) are hard to reverse once workspaces and keys exist in the wild. Routing-policy R11 puts security calls in the strong-tier bucket explicitly. |
| 3 | Launch announcement for the newsletter | `fabius-mercatus` (positioning, message-to-awareness match, copy structure) under `fabius-parcus` (lean prose) | Single draft, one pass — no funnel/channel build, just the announcement copy itself | **Mid** | Needs real judgment (audience is existing users, not cold traffic; the hook is "the API you asked for," proof over adjectives) but it's a single bounded artifact with low downstream blast radius — a subject line or CTA can be revised in the next newsletter. Doesn't need the strong tier's architecture/security-grade reasoning. |
| 4 | Decision record for the team | `fabius-archivum` (project memory / decision record — provenance, dated, attributable) | Single-pass structured log: template fill from decisions already made in parts 1–3, no research, no new judgment calls | **Cheap** | Mechanical once the upstream decisions exist: summarize what was decided, by what reasoning, what's still open. Low-judgment transcription work — exactly what R11 reserves the cheap tier for. Should be updated (not re-generated from scratch) each time a part above lands. |
